# G3 — retired backends drain; the store fence (tasks 3.1 and 3.2)

- Change: `openspec/changes/sink-credential-rotation/` · branch: `feat/sink-credential-rotation` ·
  pre-task sha: `f08fb2b12` (the G2 commit, the red base) · started: 2026-10-20
- Satisfies: tasks.md 3.1 (tests) and 3.2 (implementation); SCR-3 · design: *Pool entries with
  holders*, *Fingerprint and acquire* step 4 · constitution: none (repo rules `AGENTS.md`,
  `docs/development/spec-workflow.md`)
- Smallest coherent change: a pooled entry counts its holders; every path that drops an entry goes
  through `retireLocked`, which removes it at once and closes it only when nobody holds it (else
  the last, idempotent release closes it); the TTL prune skips held entries; stores pass a
  per-sink generation fence, so an older build neither replaces a newer entry nor re-populates a
  retired key.
- Deferred items from earlier groups, covered here: G1 b-N2 (last writer wins between two
  concurrent builds) → row 5; G2 round-1 NOTE (retire now closes before the rebuild) → rows 1-4,
  8; G2 round-2 NOTE (a stale metadata read can retire a newer entry) → rows 10-11. The stale-read
  interleaving was real on the G2 commit (red below), so it is fixed here: the acquire records the
  key's generation before its metadata read. When a pooled entry does not match and the
  generation changed since then (the entry was stored after the read began, so the read may be
  older than it), the acquire does not retire on that read but reads the metadata again
  (`observeAndLookup`, at most `poolReadAttempts = 2` reads). The re-read begins after the entry
  was stored, so it is at least as new as the entry's snapshot, and the last attempt always acts
  on what it read, as the design's retire rules say. The not-found/empty retire follows the same
  rule. If the re-read fails for another reason (timeout, cancelled, forbidden), the first
  successful read stands and the entry it did not match is retired if still pooled (added after
  review round 2). Accepted residual: if yet another acquire stores between the re-read and its
  lookup, the forced last attempt retires that newer entry; its holders drain and this acquire
  rebuilds from a full read taken after the retire, so it costs one extra build, never a stale
  backend in use. (Round 1's first version skipped the retire without a re-read; reviewer-a showed it could
  keep an older entry after a read that observed the change, see *Review*.)
- Generations: a key gets a fresh value from the pool-wide counter on its first read, so a recorded
  value is never 0, and a key that aged out (absent, reads as 0) never matches a recorded value.
- Files: `internal/sink/backend_pool.go`. Tests: `internal/sink/backend_pool_drain_test.go` (new).

## Learnings

Class: guidance, sensor.

- G3: a guard that skips a retire on "the pool changed since my read" must not drop the read's
  observation: re-read instead, and keep the first observation when the re-read fails. Two
  review rounds each found one more interleaving; enumerate the read outcomes (ok, gone, other
  error) for every attempt before review.
- G3: a fence keyed on "value unchanged" needs values that are never reissued, including after
  aging out: give absent keys a fresh value on read, never let absent read as a recordable value.
- G3: a barrier only after the metadata read lets late goroutines hit a stored entry, so a
  "concurrent rebuild" test may build nothing surplus; hold every goroutine in the factory too
  and assert the build count, or a surplus-close mutant survives.
- G3: a mutant that deletes a line can be vacuous (dead code); check that the mutated line is
  reachable with a different value before citing it.
