### What "a manager matches a file" means

At least one `managerFilePatterns` hit on a tracked file AND at least one dependency extracted by
its `matchStrings` from those files. Renovate's own `extract` on today's tree (base `b834dbd15`)
shows why the second half is needed: 29 dependencies, none from the gitleaks or shellcheck manager;
`.github/workflows/ci.yaml` is matched by both and logged twice as `No dependencies found in file
for custom regex manager`. Their patterns hit; their URL regexes find nothing, because CI no longer
downloads `releases/download/v…/gitleaks_…tar.gz`: it calls `hack/install-*.sh` with a version env.
Also uncovered today: `Makefile:184`, `hack/tooling/.custom-gcl.yml:6`, both pre-commit revs, both
installers, `release.yaml:420` (the github-actions manager bumps the action, not its `version:`
input) and `hack/verify-changelog.sh:11`.

### Mechanism for 3.2: a model of Renovate, not Renovate in `lint`

Chosen: python3 (already used by other guards, preinstalled on the runner) reads `renovate.json`
itself and evaluates the custom regex managers and the `packageRules` order. There is no copy of
the regexes, so the copy-drift case the task names (`\n` escapes) cannot arise; a control case
shows the model reads both newline spellings.

Why not Renovate in `lint` (costs measured 2026-10-16):

| Need | Cost |
| --- | --- |
| install (cold npm cache, `npm install renovate@44.115.4`) | 40 s, 284 MB download, 349 MB on disk |
| `extract` dry-run (liveness, coverage) | 3 s per run, no network |
| grouping (`groupName` is applied at lookup) | `lookup` dry-run: GitHub API for every dependency, 6 s here, needs a token (absent on fork PRs, rate-limited without one) |
| `--self-test` | one Renovate run per mutant (about 30 renovate.json mutants) |

The install alone is under the dispatch's two-minute bar, but grouping needs `lookup`, which makes
the `lint` job depend on the GitHub API and a token, and the self-test would multiply it. The model
costs about 0.2 s per run with no network.

Trade-off, recorded: the model can drift from Renovate's semantics. Bounds on that:

- it fails closed on any shape it does not implement: an unknown manager key or `customType`, a
  `matchStringsStrategy` other than `any`, a lookbehind (not RE2), a regex flag other than `i`, a
  glob with braces or classes, a template helper, an unknown `match*`/`exclude*` matcher, and a
  `groupName`/`enabled` rule gated on `matchUpdateTypes`;
- it was checked against Renovate on this tree: on today's tree and on the final tree the model's
  dependencies (file, depName, currentValue) are **identical** to Renovate's `extract` (29 and 41;
  rows 2 and 13), and its groups equal Renovate's `lookup` branches (row 14);
- not modelled (believed harmless today): presets from `extends` (`config:recommended`) that add
  rules or managers; non-custom managers' dependencies (a rule that pulled a github-actions
  dependency into `shellcheck` would go unseen); minimatch case and brace semantics.

1. Locality: yes, two files named by the tasks (`renovate.json`, the guard).
2. Change surface: about 480 guard lines for three checks plus 32 cases; most are self-test cases
   and the python model (~170 lines), which replaces a Renovate install in CI.
3. Duplication: no; site lists reuse the DTP-1/DTP-3 scanners; the case harness is reused.
4. Second way: yes, a second Renovate evaluator next to Renovate itself; justified in *Mechanism*
   (no network or token in `lint`), bounded by fail-closed shapes and the recorded equivalence.
5. Coupling: the guard now knows `renovate.json`'s shape and each tool's depName (`TOOL_DEPS`); that
   knowledge is the requirement.
6. Abstraction: no; `consistency_go_toolchain_test.sh` still owns the go group's position.
7. Debt for green: `ALSO_RED` on two earlier cases and one control turned mutant (see *Test
   changes*); each reflects a real DTP-4 red, not a widened match. `renovate.json` was widened for
   quoted repo URLs and unquoted env values because the DTP-3 readers accept those forms.
8. Legibility: the model is one python block with named helpers; messages name manager, file and
   line.

Easier next: adding a pinned tool now fails until a manager covers it. Harder: a `renovate.json`
shape the model does not know (a new matcher, a preset rule) fails the guard until the model learns
it.

## Appendix: the Renovate probe (`/tmp/g3/renovate-probe.sh`)

```bash
#!/usr/bin/env bash
# Renovate 44.115.4 local dry-run on a copy of a tree's tracked files (working-tree content).
# Usage: renovate-probe.sh <repo> <label> <dry-run mode: extract|lookup> [prep-script]
set -euo pipefail
repo="$1" label="$2" mode="$3" prep="${4:-}"
R="${HOME}/.npm/_npx/05eeecd92f4e18e0/node_modules/renovate/dist/renovate.js"
c="/tmp/g3/copy-${label}"
rm -rf "${c:?}"
mkdir -p "${c}"
(cd "${repo}" && git ls-files -z | tar --null --ignore-failed-read -T - -cf - 2>/dev/null) | tar -xf - -C "${c}"
cd "${c}"
if [[ -n "${prep}" ]]; then bash "${prep}"; fi
git init -q
git add -A
git -c user.name=t -c user.email=t@t.invalid commit -qm copy
export RENOVATE_DRY_RUN="${mode}" LOG_LEVEL=debug LOG_FORMAT=json
export RENOVATE_ENABLED_MANAGERS='["custom.regex"]'
node "${R}" --platform=local >"/tmp/g3/renovate-${label}.jsonl" 2>&1
```
