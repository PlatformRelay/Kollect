## Design (what the guard does)

- **Pins scanned** (verified 2026-10-15, plain run prints them): Makefile `$(call go-install-tool,…,<pkg>,$(VAR))` with `VAR` evaluated by make itself (`make --eval 'kollect-print-var-%: …'`, so the derived `ENVTEST_VERSION=release-0.24` is read as the build reads it); `go run|install [-flags] <pkg>@<ver>` in `Taskfile.yml` (`{{.VAR}}` resolved from top-level vars), `.github/**/*.y?ml` and `hack/**` except `hack/test/`; `hack/tooling/.custom-gcl.yml` plugin `module`/`version` pairs. `@latest` is not a pin and is skipped (`hack/demo/hero/record.sh` vhs, `hack/migrate-chart-path.sh` cosign hint). Real tree: kustomize v5.8.1, controller-gen v0.20.1, setup-envtest release-0.24, golangci-lint v2.14.0, go-arch-lint v1.19.0, govulncheck v1.9.0, gum v0.17.0 (hack/demo, two files), logtools v0.10.1 (plugin). Cross-checked against `grep -rnIE 'go (run|install)[^|;&]*@'` over the repo minus `.git`, `bin`, `references`, `docs`, `openspec`, `node_modules` (verified 2026-10-15): same set, plus comment lines with `.../cmd/operator-sdk@version` (not a pin; operator-sdk is a checksum-verified binary download).
- **Resolution**: `go mod download -json <module>@<ver>` in an empty temp dir, `GOWORK=off`. A package path tries the longest module prefix first; the package directory must exist in the module that resolved (a typo below a real module does not pass). A lookup failure (typo, network, `GOPROXY=off`) is a FAIL with go's error text.
- **Newer Go**: the `go` directive of the downloaded go.mod is compared with go.mod's (`sort -V`). Found while testing: under `GOTOOLCHAIN=go1.27.2`, `go mod download` itself refuses a module whose go.mod needs a newer Go ("requires go >= 1.99.0 (running go 1.27.2 …)"), so that error is parsed and reported as the newer-Go failure, naming tool, version, module and both Go versions.
- **Toolchain**: every go command runs with `GOTOOLCHAIN=go<go.mod version>` (exactly that Go, never another, no `+auto`); the guard first checks `go env GOVERSION` equals it. The spec says "GOTOOLCHAIN=local with the Go of go.mod"; in CI setup-go installs that version so both are the same toolchain, and on a host whose local Go differs (this one: local go1.27.1) `local` would test the wrong Go. Believed equivalent for CI; reviewers to judge.
- **Smoke run** (analysis tools, once per pinned version): golangci-lint is built by the repo's own `make golangci-lint LOCALBIN=<fresh cache dir>` (the custom build with the logcheck plugin), then `run --default=none --enable=govet ./internal/envtestassets/` with the repo config; govulncheck `-format json ./internal/envtestassets/` (exit reflects errors, not findings); go-arch-lint `check --arch-file .go-arch-lint.yml` on the whole module. Non-zero exit, or a `panic:`/`fatal error:` line, is a FAIL. Build failures fail closed. Tools are cached per run (temp dir) or in `KOLLECT_TOOL_PINS_CACHE` (the self-test shares one across mutants); the golangci cache key includes the Makefile and `.custom-gcl.yml` contents, so a stale `bin/golangci-lint` can never stand in (the Makefile's own `$(GOLANGCI_LINT)` file target would skip a rebuild after a version change).
- **Presence**: golangci-lint, govulncheck and go-arch-lint must each be found by the scan; an empty or partial scan fails. `.custom-gcl.yml` `version:` must equal the Makefile `GOLANGCI_LINT_VERSION`.
- **Self-test**: copies the tracked tree (`git ls-files` | tar) per mutant; the no-op copy must pass; each mutant must red with its own sentinel message. The newer-Go fixture is a module served from a `file://` GOPROXY built at run time (`kollect.invalid/newgo@v1.0.0`, `go 1.99.0`); the `go` command reads it, so the fixture is checked by the tool it feeds. It is removed from the shared module cache afterwards.

## Maintainability

1. New abstraction? No: one script, same layout as `consistency_go_toolchain_test.sh`.
2. Duplicated logic? The Makefile pin is read by make itself, not re-parsed; the golangci build reuses the Makefile target.
3. Hidden coupling? Yes, to `./internal/envtestassets/` and `.go-arch-lint.yml` — named constants at the top; a missing package fails the smoke run (fails closed).
4. Hard to change? Adding an analysis tool = one `analysis_tool` case + one `smoke` case + presence list.
5. Silent failure modes? Lookup, build and smoke failures all FAIL; empty/partial scans FAIL via the presence check.
6. Untested branches? `<unresolved:…>` (a non-literal version such as `${VER}`) has no mutant; the golangci version assertion is reached only through hand mutant f2.
7. Performance? Plain 26 s warm / 88 s cold build cache; self-test ~5 min warm (13 mutants; Makefile-touching mutants rebuild golangci). Recorded for 6.1: the self-test is the slow step and could run as its own parallel step.
8. Side effects? Writes only under one temp dir removed at exit; the newer-Go fixture enters the shared module cache during the self-test and the EXIT trap removes it. `<tree-root>` mode runs that tree's Makefile: trusted trees only (usage says so).
Easier or harder: easier — the G1 failure (three analysis tools broken by a Go bump) now reds in one named step.

## Learnings

- tooling: in bash, a helper that records state in a global (`TMP_DIRS+=…`) does nothing when called as `$(helper)`; register cleanup roots in the parent shell and let helpers only create under them. Proposed for the next guard prompt.
- tooling: `go mod download` under an exact `GOTOOLCHAIN=goX` refuses a module whose go.mod needs a newer Go ("requires go >= …") — parse that error, the GoMod file is never reached.
- sensor: a smoke run must build each pin at ITS version; a shared build target silently substitutes the Makefile's version. Assert the built binary's version.
- guidance: never wait with `pgrep -f <pattern>` when the pattern is in the waiting command itself; wait on PIDs (`wait "${pids[@]}"`). (Orchestrator-reported; an 80-minute hang.)
