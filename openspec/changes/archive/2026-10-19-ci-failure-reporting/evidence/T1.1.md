### P4 — cancelled runs and the started rule (verified)

```sh

```

| Run | Conclusion | Jobs | Shape |
|---|---|---|---|
| 37910176249 | `cancelled` | 0 | `jobs: []` |
| 37910175837 | `cancelled` | 6 | every job `status: completed`, `conclusion: cancelled`, `steps: []`; `startedAt` **set** (and later than `completedAt` on two jobs); one matrix job keeps its unexpanded name `e2e-${{ matrix.scenario }}` |
| 38548919239 | `cancelled` | 5 | every job has steps; one `cancelled` (6 steps), four `success` |

Rule for 3.1: a job **started** iff its `steps` array is non-empty. `startedAt`, `completedAt` and
`status` do not tell (set and `completed` on jobs that never ran). A `cancelled` run is failure
class iff at least one job has non-empty `steps`; a run with no jobs, or only step-less jobs, is
the no-op class. Survey of the 8 cancelled runs in this repository's last 400: step-less
`cancelled` jobs also sit inside runs that did start (Docs 37585437628 `Deploy to GitHub Pages`,
CI 37585437571 `sonarcloud`), so the rule asks whether **any** job has steps, not whether all do.

## Findings for later tasks

- **F1 (3.2, 3.3; verified):** in gh 2.98.0 any `--label` on `gh issue list` turns the query into
  GraphQL `search` (IssueSearch), the same index `--search` uses. So a lookup with `--label` breaks
  CFR-4's "issue list API, never `--search`" in substance. The only spelling that finds
  `github-actions` issues through the list API (IssueList) is
  `gh issue list --author 'github-actions[bot]' --state all --limit <N> --json ...` **without**
  `--label`; the reporter then checks the label and `author.login == "app/github-actions"` in the
  JSON. `--author app/github-actions` and `--app github-actions` return 0 on the list API (they
  work only through search). This is the argv 3.2's "lookup argv equals the spelling recorded in
  1.1" pins. Side effect: `--limit` counts every `github-actions` issue, not only `ci-failure`
  ones, so the completeness check (exit non-zero at the limit) needs a limit sized for that.
  CFR-4's text needs no change (it says the issue is found by label, author and marker, which a
  client-side label check satisfies); the orchestrator may want this argv named in spec.md.
- **F2 (3.1–3.3; verified):** comment authors differ from issue authors in `gh issue view --json
  comments`: `{"login":"github-actions"}` without `is_bot`, against `app/github-actions` +
  `is_bot: true` for issues. A matcher written for the issue shape rejects every bot comment and
  never sees a marker after the first. REST comments carry `user.login == "github-actions[bot]"`
  and `user.type == "Bot"`, which no user login can match (`[` is not allowed in user logins,
  **believed**). Recommend reading comments through REST, or matching `github-actions` there; the
  fake `gh` must serve the shape of whichever command 3.3 uses.
- **F3 (3.1; verified):** started-job rule as in P4 (non-empty `steps`); `startedAt` is a trap.
- **F4 (2.1, 2.2; verified):** `--log-failed` labels every line `UNKNOWN STEP`, so the failed step
  name for the body must come from the jobs JSON (first step whose conclusion is not `success` or
  `skipped`), never from the log. Two failed jobs gave 288 KB of log, far over the 60000-character
  body cap, so truncation is the normal path, not an edge case. The first line carries a BOM.
- **F5 (3.2; verified):** `Go patch lag` has no scheduled run yet (one `workflow_dispatch` run, #1,
  2026-10-16), so `gh run list --workflow .github/workflows/go-patch-lag.yaml --event schedule
  --status completed --limit 1` returns `[]`. spec.md does not say what the reporter does on an
  empty list; it can happen only if a non-scheduled event slips past the guard. Recommend: exit
  non-zero with no write, and a 3.2 case for it.
- **F6 (verified):** `gh run view` on a run cancelled before start returns `jobs: []` or step-less
  jobs; `--log-failed` there was not probed (no failed job to fetch).
- **F7 (believed):** no `timed_out` run found (last 400 runs here, `--status timed_out` on seven
  large public repositories, and about 80 failed runs scanned for a job-timeout step pattern). The
  timed-out copy uses the docs enums: `workflow_job` conclusion includes `timed_out`; the steps
  enum does not, so the running step is `cancelled`. The builder should treat any job conclusion
  other than `success`, `skipped` or `neutral` as failed, so the fixture's choice does not decide
  the outcome.

## Learnings

- tooling: `gh issue list --label` (gh 2.98.0) runs GraphQL search; only a label-free
  `--author 'github-actions[bot]'` uses the issue list. Check `GH_DEBUG=api` for the operation
  before calling any gh argv "not search" (F1).
- tooling: in a jobs list, `startedAt` is set on jobs that never ran; a job started iff `steps` is
  non-empty (F3).
- tooling: issue authors and comment authors from `gh issue view --json` differ
  (`app/github-actions` + `is_bot` against `github-actions`) (F2).
- tooling: the Bash tool's zsh does not word-split `$var`, so a loop over flag strings passes one
  argument; run such loops under `bash`.
- guidance: a codex review leg here has no network; live-shape checks stay with the implementer.
