0.4 Probe Renovate's behaviour (DUA-3, DUA-7, DUA-8, DUA-9) with a local Renovate of the version
chosen for DUA-3, run outside the repo on a committed scratch copy of the tree
(`--platform=local`; `RENOVATE_DRY_RUN=extract`, then `lookup` with a token from `gh auth token`
passed by environment, never printed or written). The scratch copy carries the planned
`renovate.json` and `renovate.yaml` and deliberately older pins so that every case below produces

patch, an older `azure/setup-helm` `version:` input and an older `HELM_VERSION`, an older action
SHA, and an older `renovate-image`. Record per branch: name, upgrades, update types, the resolved
`automerge` and `groupName`. Expected: (a) the `renovate-image` input is extracted as a docker
dependency with tag and digest, in a branch of its own, `automerge` false, and with the window
moved to a weekday other than the probe's day it is reported as not scheduled; (b)
`release.yaml`'s Helm input (`depName` `helm`, `packageName` `helm/helm`) and every
`HELM_VERSION` land in `renovate/helm`; (c) only digest-only `dockerfile` or `devcontainer`
branches carry `automerge: true`; the `go toolchain` branch is shown to hold both the digest and
the `go` directive upgrade, and carries `automerge: false`; (d) action `src/docker.ts` at v46.3.10
uses a `renovate-image` that holds `:` as the whole reference (record the tag's commit SHA); (e)
read the pinned Renovate's source and record, with file and line: GitHub `getBranchStatus` returns
pending (not green) with no statuses and no check runs, red on a failed run, pending on a queued,
cancelled or timed-out run; PR automerge needs green; branch `automerge` is every upgrade's
`automerge`; a branch behind its base is rebased before reuse when `rebaseWhen` is
`behind-base-branch`. Evidence `evidence/0.4.md`. A premise that turns out false is a
SPECIFICATION finding: stop and report

## Observations for later tasks

- **Tag changes share the `docker images` group with digests.** In `mon` the debian digest
  (`Dockerfile`) and the debian minor tag change (`Dockerfile.pipeline`) land in one
  `renovate/docker-images` branch, so the digest is not auto-merged (DUA-7 scenario "a group
  mixing one of those with a digest"). Today's Dockerfiles carry no versioned tag that can move
  (`bookworm-slim`, `static:nonroot`, golang in `go toolchain`), so the group is digest-only in
  practice (`ctl`). 2.4 should reuse the `ctl` shape as the positive case.
- **Pending upstream digests today.** `debian:bookworm-slim` is at `sha256:7ff6ba31…` upstream
  (repo: `7c7b2c96…`) and `gcr.io/distroless/static:nonroot` at `18f4cc26c9ff…`: the first
  digest-only PR after merge (the DUA-7 post-merge row) may not need to wait for an upstream push.
- **Action v46.3.10 is new.** Published 2026-10-26T02:22:12Z, about 8 hours before this probe.
  v46.3.9 (2026-10-19) and v46.3.4 onward also honour the full reference. The spec fixes "v46.3.10
  or later"; whether to take a tag this young is for 2.1 / the operator, not a probe finding.
- **The dashboard checkbox bypasses the image window** (`update/branch/index.js:255`,
  `!dependencyDashboardCheck`): a maintainer's tick on the dashboard can create the image PR
  outside the window. A human action, consistent with DUA-3; worth one line in the docs (3.1).
- **Check-run permission.** If the token cannot read check runs (403), `getBranchStatus` falls back
  to commit statuses alone (`github/index.js:765-767`); with none it returns pending, so the
  failure is closed (no merge), not open.
- **DUA-9 scenario wording.** The scenario "Helm release" names the branch `renovate/helm`. A
  major Helm release (v4.3.1 is out) lands every Helm pin, `release.yaml` included, in one
  `renovate/major-helm` branch instead (Renovate's default `separateMajorMinor`; same group). The
  requirement ("land in one PR") holds; the scenario's branch name is exact for minor and patch
  releases only. Disposition: deferred to the orchestrator as a spec-wording precision (stage B or
  2.4), not a false premise; 2.4 should assert both branch names.
- **`local` platform limits.** A local run never reaches `processBranch`, so 2.4 can re-check
  grouping and `automerge` this way but not schedule or merge behaviour (use `isScheduledNow` as
  here, or a post-merge row).
