## 7.1 — gh output must be one JSON document of the expected shape (B1)

Change: `need_json <file> <jq test> <call>` in `hack/ci/ci-failure-report.sh` runs
`jq -e -s 'length == 1 and (.[0] | <test>)'` after each of the three reads (run list and issue
list: an array; comments: an object whose `comments` is an array) and dies with "`<call>` did not
return one JSON document of the expected shape". The fake gh serves `${FAKE_GH_DIR}/raw-<kind>`
verbatim with exit 0 for run-list, issue-list and issue-view.

Cases (`hack/test/ci_failure_report_test.sh`, case names `gh-output-<read>-<shape>`): for each of
the three reads, four shapes: empty (0 bytes), garbage (`not json`), two documents, wrong type
(`{"total": 0}`; for comments `{"comments": "x"}`). Each must exit non-zero, write nothing, make
no call after that read, and print the message above.

Red (before the reporter change; `CFR_SELFTEST_ONLY='gh-output-.*' bash
hack/test/ci_failure_report_test.sh`, exit 1). Behaviour reds, on the claim's reason:

```text
FAIL: gh output: run-list empty: expected a non-zero exit, no write and 'run-list' as the last call, got exit 0, writes 'none', last call 'run-list'
FAIL: gh output: run-list garbage: expected a non-zero exit, no write and 'run-list' as the last call, got exit 0, writes 'none', last call 'run-list'
FAIL: gh output: issue-list empty: expected a non-zero exit, no write and 'issue-list' as the last call, got exit 0, writes 'create', last call 'create'
FAIL: gh output: issue-view empty: expected a non-zero exit, no write and 'issue-view' as the last call, got exit 0, writes 'comment 10', last call 'comment 10'
FAIL: gh output: issue-view two: expected a non-zero exit, no write and 'issue-view' as the last call, got exit 0, writes 'comment 10', last call 'comment 10'
FAIL: gh output: issue-view wrong: expected a non-zero exit, no write and 'issue-view' as the last call, got exit 0, writes 'comment 10', last call 'comment 10'
```

The other six (run-list two and wrong, issue-list garbage, two and wrong, issue-view garbage)
already stopped, by accident (a jq error or an arithmetic error under `set -e`), and were red only
on the missing message: the empty issue list opened a duplicate issue and the empty, two-document
and wrong-type comments each wrote a duplicate comment, as B1 said.

Green after the change: same command, exit 0, 12 `ok` lines.

Self-test mutants added (judged by the named case, each red with its expected message in the
final self-test run): each read's `need_json` call replaced by `:` (3 mutants, judged by the empty
case of that read); `length == 1` widened to `length >= 1` (issue-view two); the comments-array
clause dropped (issue-view wrong).

Scope note: the jobs read (`gh run view --json jobs`) is not one of the three reads the task names.
Its empty output is already refused for the failure class by the body builder (`.jobs | type`
check, exit 2, the reporter dies with "the issue body could not be built"), and for a cancelled run
it reads as no started job, a no-op (no write). **Believed** harmless, left as is.

Test change (self-test, 5.1's port of G3 M17): the mutant `|| die "gh issue view --json comments
failed"` → `|| true` survived once `need_json` existed (first self-test run, exit 1:

case and message. Listed under *Test changes*.

## 7.3 — concurrency at job level (B3)

Change: the `concurrency:` block (same group and `cancel-in-progress: false`) moved from the top
of `.github/workflows/ci-failure-report.yaml` into the `report` job, after its `if:`, with the
comment saying why. The wiring assertion now reads `[workflow concurrency, job group, job
cancel-in-progress]` and wants `[null, "ci-failure-report-${{ github.event.workflow_run.workflow_id
}}", false]`. Mutants: G4 W4 now sets the job's `cancel-in-progress: true`; new B3 mutant moves
the block back to workflow level. CFR-1 names the group and `cancel-in-progress`, not the level
(spec.md, Scenario "Concurrent reports"), so the spec text is unchanged.

before it enters its concurrency group; not observable before merge): a run whose job is skipped
by the `if:` (a dispatched or fork run) never enters the group, so it cannot displace a pending
scheduled report.
