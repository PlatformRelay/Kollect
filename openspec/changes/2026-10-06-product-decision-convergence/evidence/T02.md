Notes:
- Count source is the production read the controller already uses (`collectedCount(ct, matched)` →
  `Engine.ItemCount(ns, ct.name)`), seeded through `collect.NewStore()` + `store.Upsert` with 17
  items, exactly as `kollectclustertarget_unit_test.go:30-42` does; no informer machinery is
  touched (engine with nil clients, no Start), so the seeded count is deterministic.
- The harness drives the reconcile status-write seam (`setReady` / `setDegraded`) — the same layer
  the namespaced parity anchor uses (`kollecttarget_collected_count_test.go`) and the existing
  cluster filter-status hatch tests (`kollectclustertarget_status_test.go`). No production symbol is
  referenced that does not exist; no helper that T07 will rename is called.
- The message is built with the shared `readyConditionMessage` helper so a seeded byte-identical
  condition cannot drift from what the reconcile would write.
- Deliberate mid-flight state (T07 resolves): CRD manifests (`config/crd/bases`, `charts/kollect/crds`
  via `make manifests`), `docs/crds/kollectclustertarget.md` and the glossary are NOT regenerated in
  T02 — tasks.md assigns the codegen ripple to T07 ("regenerate CRDs (`make generate manifests`)");
  `loop.md` pins the codegen-drift gate (`task verify`) to T07/T09. Deepcopy IS regenerated here
  (adding pointer fields without updating the generated copy silently drops the fields in every
  fake-client store round-trip — the scaffolding would be broken by construction).

## Maintainability

1. Locality: yes — one API types file (+ its generated deepcopy), one new test file; the test
   reuses the existing same-package harness (`clusterTargetStatusClient`, `readyConditionMessage`).
2. Change surface: ratio ~1:1 — 4 task-text clauses → 1 types file, 1 generated file, 1 test file
   with 5 tests; the 5th test is the spec's one-write scenario under the TSP-1 id the task cites.
3. Duplication: the two engine builders share one body (`clusterCountEngine` delegates to
   `clusterCountEngineFor`); target/message/count fixtures reuse the namespaced parity file's
   shapes (fresh + seeded-Ready) and the cluster status tests' counting client — nothing copied
   that exists as a function already.
4. Second way: no — the tests drive the production seam the namespaced parity suite already uses
   (`setReady`/`setDegraded`), no new helper layer, no config knob.
5. Coupling: the API surface gains the two status fields the spec fixes (that is the change);
   no module learned anything new — the test file is the only reader of the fields until T07.
6. Abstraction: no bypass — the count is seeded through the store exactly as the suspend test does,
   the condition through the shared `readyConditionMessage` helper, the write observed through the
   shared status-counting client.
7. Debt for green: none — nothing was bent to satisfy a sensor; the reds are the required red of a
   test task and the guards pass for a verified structural reason.
8. Legibility: each test is named after its claim, its failure line states that claim, and the file
   header names the parity intent; the seeded-Ready fixture mirrors the existing filter-status
   fixture a reader of this package already knows.

(`filterChanged || countChanged`). Harder next: the test file owns two engine builders and three
