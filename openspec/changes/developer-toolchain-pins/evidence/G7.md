## The rule

`renovate.json` `packageRules[last]`: `matchManagers: ["github-actions"]`,
`matchDepTypes: ["uses-with"]`, `matchDepNames: ["node", "python"]`,
`matchPackageNames: ["actions/node-versions", "actions/python-versions"]`, `enabled: false`.
The names come from Renovate 44.115.4
`dist/modules/manager/github-actions/known-actions/github-releases.js` (`actions/setup-node` →
depName `node`, packageName `actions/node-versions`; `actions/setup-python` → `python`,
`actions/python-versions`; `utils.js` `parseValue` sets depType `uses-with`) and agree with the
extract dry-run below. It is the last rule, so no later rule can set `enabled` back. It sets no
`groupName`, so `go toolchain` stays the last group rule (`consistency_go_toolchain_test.sh`
green).

## Gaps

1. In the rule-off lookup Renovate 44.115.4 computed the node and python bumps but logged
   `Could not determine new digest for update.` for each (`pinDigests: true` from the
   "github actions" rule; `actions/node-versions` has no tag `24`) and the updates list came out
   empty, so this version might never have opened that branch. Not followed further; the rule
   removes the dependence on that incidental drop.
2. The model reads steps line by line (a `uses:` and its step's `with:` mapping), not as YAML;
   flow-style `with: {node-version: 22}` is not seen. It agrees with Renovate's extract on this
   tree (row 1).
3. Seen in passing, not in scope: azure/setup-helm's `version:` input is extracted as depName
   `helm` (packageName `helm/helm`), so the `helm` rule (`matchDepNames: ["helm/helm"]`) does not
   catch it and it lands in `renovate/github-actions` (rule-on lookup: v3.22.0 → v3.22.1 there),
   contrary to that rule's description.

## Maintainability

No new abstraction beyond the model's extractor; no duplicated logic (the mise check keeps its
own input reader, which reads every `node-version:` key, a superset). Easier: the guard now fails
if anyone drops or overrides the rule.
