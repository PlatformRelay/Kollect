## Task text

per-asset `<asset>.sha512` (the `.sha256` is 404), helm-docs `checksums.txt`. Stop if one is
missing.

4.2 Tests first, in the new guard's `--self-test`, with a fake `fetch_to`, per installer: given a
valid archive and a checksum file in the published format, then the installer exits 0 and the

non-zero with its checksum diagnostic and the output path does not exist (tampered download

copy of the installer with its verification removed, the tampered case fails its assertion (the

`hack/test/ci_fetch_lib_hardening_test.sh` (`verify_sha256|sha256sum`, ~779 and ~793) to accept

4.3 Verify git-cliff with `sha512sum` against `<asset>.sha512` and helm-docs against

## Design notes

- git-cliff publishes only SHA512, and `hack/lib/verify-sha256.sh` is SHA256-only. One consumer,
  and the task text and DTP-6 name `sha512sum` in the installer and in the scan, so the compare is
  inline in `install-git-cliff.sh` (mirrors `verify_sha256`'s messages) rather than a new
  `verify_sha512` helper. helm-docs reuses `verify_sha256`. Both use `fetch_to`.
- Both installers fetch the checksum before the tarball (as `install-gitleaks.sh` does); the valid
  case asserts that order.
- The expected digest is taken only from the line naming this asset (git-cliff: `$2 == asset` or
  `*asset`, then must be 128 hex; helm-docs: `$2 == asset`, must be non-empty).
- Widening the hardening gate's scan to `sha512sum` adds a stronger verifier to what counts as
  verification; it exempts no installer and is not an allow-list widening. The allow-list itself
  (`UNVERIFIED_BY_DESIGN`, and the guard's `UNVERIFIED_LIMIT`) shrinks to empty.
- The `other-asset` case was added after the first hand-mutant pass found three survivors (below);
  it is red on the pre-task installers too.

## Maintainability self-check

1. New abstraction? Test helpers `inst_*` in the self-test only; no product abstraction.
2. Duplicated logic? The git-cliff compare mirrors `verify_sha256` (7 lines); justified above.
3. Hidden coupling? The fake `fetch_to` mirrors the real failure message `failed to download ... from <url>`; a change to that message reds the missing-checksum case loudly, not silently.
4. Dead code? No; the NOTEs and both list entries are removed.
5. Magic values? `99.0.0` fixture version, stated as never a release.
6. Error paths tested? Tampered, missing, other-asset; real network failure is `fetch_to`'s own gate.
7. Platform assumptions? `sha512sum` is GNU coreutils; stock macOS lacks it (deferred: BACKLOG DTP-SHA512-MACOS, triage R14).
8. Scope creep? The other-asset case goes beyond the task text; it kills three mutants that survived otherwise.

## Harness gaps

- `ci_fetch_lib_hardening_test.sh` and `ci_install_helm_hardening_test.sh` have one mode only;
  "both modes" applies to the toolchain-pins and workflow-security guards.
- The installer tests run Linux x86_64 asset names (faked `uname`); the Darwin and arm64 paths are
  covered by the 4.1 URL probe only, not by an install.

## Learnings

- tooling: a gzip header's MTIME byte (offset 4, after `gzip -n`) is a tamper that still extracts,
  so a tampered-archive test fails on the checksum and not on `tar`.
- sensor: a per-asset checksum file has one line, so "take the line naming the asset" survives every
  fixture until a case files the right digest under another name.
