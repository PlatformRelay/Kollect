## How the rule reads a comment (design, verified by reading the code 2026-10-16)

- Scope: every full-line comment and every inline comment (text after a blank and `#`) in
  `mise.toml` and `Taskfile.yml`.
- Pin: a `mise.toml` `[tools]` key, or a `Taskfile.yml` `<X>_VERSION:` with a literal version.
  `HELM_VERSION` is at `Taskfile.yml:33` today (the task text's `:31` predates 2.2's two added
  lines).
- Attached: the unbroken run of comment lines directly above a pin (a blank line or any other line
  breaks it), or inline on the pin's line.
- Version: a dotted or quoted number (`v` and a `-rc1`-style suffix allowed), or a bare number right
  after a pin name in that file (`node 20`; review round 1). The word right before it is the tool
  it names. Allowed only when attached and the word is the pin's key, its CI input name
  (`node-version`, `python-version`, setup-task's `version`) or, for a Taskfile pin, its tool
  (`HELM_DOCS_VERSION` -> `helm-docs`), at the pin's value with a leading `v` stripped.
- Count: a number followed by `occurrences`, `sites`, `places` or `workflows`, any case,
  anywhere: red.

## Harness gaps

- A bare number is a version only right after a pin name in the same file: `# gitleaks 8` in
  `mise.toml` passes (gitleaks is no pin there). Dotted and quoted numbers are always read.
- The rule fails closed on prose: any dotted number in a comment (`127.0.0.1`, `Go 1.22`) reads as
  a version and reds unless it sits beside its pin. None exists today (plain mode green); the
  message names the line. Review round 1 (paid leg) asked only that this be recorded.
- Only the word right before a version is taken as the tool it names.

## Maintainability

1. New abstraction without a second user? No: two functions, one call site, the guard's pattern.
2. Duplicated logic? `pin_of` re-reads `[tools]` keys like `mise_tool_sites`; the awk needs the line
   numbers of every pin in one pass, which `mise_tool_sites` does not give. Justified.
3. Function over complexity threshold? The awk program is ~70 lines in four functions. Acceptable
   for a bash guard; the guard's other awk blocks are similar.
4. Dead code or flags? No.
5. Names say what they do? Yes (`comment_findings`, `check_comments`, `pin_of`, `names_of`).
6. Error paths silent? A missing file is skipped; `check_mise` already reds a missing `mise.toml`,
   and every other check reads `Taskfile.yml`.
7. Comments claim more than the code? Header and step comment checked against the code; review
   to confirm.
8. Portability: POSIX ERE only, run under mawk and busybox awk.

## Learnings

- class: sensor. A comment rule that reads "a version" needs a definition of a version; agree it
  with the spec before writing the parser (bare majors and `-rc1` suffixes both slipped in round 1).
- class: sensor. A new rule over a file that earlier mutants edit breaks those mutants' one-clause
  rule: grep the self-test for every mutant touching the file and run it before writing new cases.
- class: sensor. Hand-mutate each regex alternative: one survived as redundant (the quoted-number
  alternative) and was removed.
