### 3. Coalesce skip and the export interval (verified 2026-10-19, P4 and reading) — SPECIFICATION finding

- `perSinkCoalesceTracker.shouldSkip` (`internal/controller/per_sink_export.go:55-93`) skips while
  `now - lastExport < interval` and stops skipping when the interval is due: P4 prints
  `interval=30s … skip@+interval=false` and `interval=24h0m0s … skip@+interval=false`. The call
  site is `kollectinventory_controller.go:360-370`, the cluster reconciler's `:309`.
- But for `interval == 0` it returns `true` unconditionally once generation, checksum and
  `requestedAt` match (`per_sink_export.go:85-87`): P4 prints `interval=0s skip@+1s=true …
  skip@+25h=true nextDue@+1s=30s`. `0s` is a valid, documented value ("material-change only",
  `api/v1alpha1/kollectinventory_types.go:27-32`, `docs/crds/kollectclusterinventory.md:62`,
  `docs/operator-manual/troubleshooting.md:392`), set on the inventory, the family sink or the ref
  (`validation.ResolveSinkExportInterval`, `internal/validation/export_interval.go:173-193`); only
  a scope floor > 0 replaces it (`:189-190`). So for a `0s` binding an unchanged inventory does not
  export again while its tracker entry lives (the in-memory entry goes on a pod restart, or when
  another binding's `record` prunes entries older than 48 h, `per_sink_export.go:37`, `:124-129`): a rotated or deleted Secret takes effect only at the next material change,
  generation bump or `kollect.dev/requestedAt` change — not "at most 24 h".
- Related (verified by reading): after a total export failure, `setInventoryDegraded` returns
  `RequeueAfter: r.exportDebounce(inv)` with a nil error (`kollectinventory_controller.go:652`,
  cluster `kollectclusterinventory_controller.go:713`); with an inventory-level
  `exportMinInterval: 0s` that is `ctrl.Result{}`, so a transient acquire error (missing Secret)
  is not retried on a timer. Believed: the status write may cause one more reconcile, after which
  nothing requeues until a material change.
- Contradicts: proposal *Non-goals* ("Rotation takes effect on the sink's next export (bounded by
  the inventory's export interval, at most `validation.MaxExportInterval`, 24 h)"), proposal
  *Assumptions* ("Exports run at least once per export interval"), tasks.md 0.1 ("so an unchanged
  inventory still exports once per interval"), and for the requeue part proposal SCR-2 ("restoring
  the Secret recovers without touching the sink"). For every interval > 0 the assumptions hold.

### 4. BigQuery v1.85.0 `Client.Close` (verified 2026-10-19, reading)

`$GOMODCACHE/cloud.google.com/go/bigquery@v1.85.0/bigquery.go:152-160`: `Close` only closes the
Storage Read client `c.rc` when `isStorageReadAvailable()` (`:139-141`, `c.rc != nil`), which only
`EnableStorageReadClient` (`:127`) sets. kollect never calls it (`internal/sink/bigquery/backend.go:97`
`bigquery.NewClient` only; `rg EnableStorageReadClient internal/` finds nothing). So for kollect,
`Client.Close` is a no-op returning nil: an operation in flight is not interrupted, and a call made
after Close still runs on the REST service. Holder draining (SCR-3) is harmless here and not
needed for correctness of BigQuery; it matters for pgx, mongo, kafka and NATS.

### 5. Git mirror, export locks, per-call auth (verified 2026-10-19, reading)

- `mirrorDirFor(cloneURL, branch)` (`internal/sink/git/mirror.go:149-161`) hashes `cloneURL +
  "\x00" + branch`; the clone URL has its userinfo stripped (`internal/sink/git/export.go:496`,
  `u.User = nil`), so a credential change does not change the mirror directory: the old and the
  rebuilt backend share one mirror.
- `withRepoExportLock` (`internal/sink/git/export_lock.go:10-29`) keys a process-global
  `sync.Map` of mutexes on the same `cloneURL + "\x00" + cloneBranch`; export (`export.go:117`,
  `:135`) and delete/release (`delete.go:109`, `:121`) take it, so two backends for one repository
  never use the mirror at once.
- Auth is passed per call from the backend (`backend.go:65`, `:77`, `delete.go:42`, `:65` pass
  `b.auth`; fetch `mirror.go:192`, clone `export.go:513`, push `export.go:429` set `Auth` from it,
  with `cfg.CABundle` per call too). Nothing stores credentials in the mirror. So a rebuilt Git
  backend fetches and pushes with the new credentials and CA.

### 6. S3 empty Secret falls back to the default chain (verified 2026-10-19, P3 and reading)

`ConfigFromSpec` copies access keys only when present (`internal/sink/s3/config.go:65-79`), and
`newClient` adds the static provider only when one of them is non-empty
(`internal/sink/s3/backend.go:159-163`), else `awsconfig.LoadDefaultConfig` keeps the default
chain. P3 with `AWS_ACCESS_KEY_ID` set in the environment: creds `nil`, `{}` and `{other: x}` all
build and resolve `source="EnvConfigCredentials" keyID="AKIDPROBEAMBIENT"`. GCS wraps S3
(`internal/sink/gcs/backend.go:27-41`), so the same holds. The partial case (other keys, no access
key) is exactly the one proposal *Non-goals* keeps.

### 7. Missing Secret error class (verified 2026-10-19, P1 and reading)

- Through the API reader, `ResolveSecret` rewrites NotFound into a plain error
  (`internal/sink/credentials.go:43-46`); wrapped as `export.go:104` wraps it:
  `acquire backend for "s": secret "db" not found in namespace "probe"`, `ClassOf` = `transient`,
  `IsTerminal` = false. A transient total failure requeues after `exportDebounce` (30 s by
  default; see finding 3 for `0s`).
- Caution for G2 (not a contradiction): the raw metadata GET of a missing Secret returns an API
  NotFound that `ClassOf` classes `terminal` (`internal/errors/errors.go:99-101`; P1 prints
  `metadata GET of missing secret: notFound=true class=terminal`). `secretMeta` must map NotFound
  to the plain `secret %q not found in namespace %q` text, as design *Errors on the acquire path*
  says, or a deleted Secret becomes a terminal, never-retried error.

### 8. Retained without contacting the sink (verified 2026-10-19, P2)

From a zero-value typed nil per registered type (every `Capabilities()` returns a constant, so a
nil receiver works; the `ExportCleaner` assertion is on the type):

| type | SupportsDelete | ExportCleaner | retained without contact |
|---|---|---|---|
| bigquery, mongodb, postgres | true | false | no (prune) |
| git, gitlab | false | true | no (release, `cleanup.go:206-208`) |
| gcs, s3, local | false | true | no (retract) |
| kafka, nats | false | false | yes (`cleanup.go:210-214`) |

So `streamSinkTypes` = {`kafka`, `nats`} matches design. The registry has no type list or

type bodyRecorder struct {
    mu     sync.Mutex
    bodies [][]byte
    accept []string
    rt     http.RoundTripper
}

func (b *bodyRecorder) RoundTrip(req *http.Request) (*http.Response, error) {
    resp, err := b.rt.RoundTrip(req)
    if err != nil || resp == nil {
        return resp, err
    }
    raw, _ := io.ReadAll(resp.Body)
    _ = resp.Body.Close()
    resp.Body = io.NopCloser(bytes.NewReader(raw))
    b.mu.Lock()
    b.bodies = append(b.bodies, raw)
    b.accept = append(b.accept, req.Header.Get("Accept"))
    b.mu.Unlock()
    return resp, nil
}

func TestProbeT01StreamTypes(t *testing.T) {

    for _, n := range names {

## Decision request

`exportMinInterval: 0s` (material-change only) is valid on the inventory, the family sink and the
ref. For such a binding an unchanged inventory does not re-export (`per_sink_export.go:85-87`), so
a rotated, deleted or emptied Secret takes effect only at the next material change, generation bump
or `kollect.dev/requestedAt` change; and with an inventory-level `0s`, a total transient failure
(the missing-Secret error SCR-2 relies on) returns `ctrl.Result{}` and is not retried on a timer
(`kollectinventory_controller.go:652`). This contradicts proposal *Non-goals* ("at most ... 24 h"),
*Assumptions* ("Exports run at least once per export interval") and SCR-2's "restoring the Secret
recovers without touching the sink" for that case.

Options:

- A (recommended): scope the wording. Proposal, design, spec SCR-1/SCR-2 and the SCR-6 docs say
  "for a binding with an interval > 0; a `0s` binding picks up the change at its next material
  change or `kollect.dev/requestedAt`", and the upgrade note says so. No code change; behaviour is
  pre-existing and documented as "material-change only".
- B: also change behaviour — requeue a transient total failure at `ZeroIntervalWatchdog` (30 s)
  when the inventory interval is 0 (`setInventoryDegraded`), so SCR-2 recovery holds for `0s`; add
  a task to G2 with a test. Re-exporting unchanged `0s` bindings on a timer would contradict `0s`'s
  documented meaning, so not that.
- C: accept as is and record a non-goal.

What unblocks: the orchestrator's choice, the spec-set edit it implies, then G1.

## Learnings

- class `spec`: a "next export bounded by the interval" claim must be checked against every valid
  interval value, including `0s` (material-change only).
- class `guidance` (for G2): the raw metadata GET of a missing Secret is an API NotFound that
  `ClassOf` classes `terminal`; `secretMeta` must rewrite it to the plain "not found" text or a
