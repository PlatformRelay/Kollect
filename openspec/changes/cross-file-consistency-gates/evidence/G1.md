## Decision request

**Question.** Bumping go.mod to 1.27.2 makes two pinned tools fail: `task lint` (golangci-lint v2.13.1, Makefile `GOLANGCI_LINT_VERSION` and `hack/tooling/.custom-gcl.yml` `version:`) fails deterministically, and `task vulncheck` (govulncheck v1.1.4, Taskfile `vulncheck`) panics in about 3 of 5 runs. CI would see the same once go.mod says 1.27.2, since setup-go installs that version. Pushing the branch as it stands turns the `lint` job red.

- **A (recommended).** Bump golangci-lint to v2.14.0 and govulncheck to v1.9.0, each in its own `:arrow_up: chore(deps)` commit, in this lane before 1.3 closes. Probes: v2.14.0 gives 0 issues on the failing package under go1.27.2 (govet only; full config with the logcheck plugin not tried); v1.9.0 ran 5/5 clean. Check the custom build first, and check whether a newer golangci-lint brings new lint findings.
- B. Do the bumps under task 2.1 (CFC-2) and leave 1.3 open until then. The branch stays unpushable (lint red) in the meantime.
- C. Revert the go.mod/devcontainer bump and move the Dockerfiles back to 1.26.9. Restores green and gives up the newer patch. Not recommended: it is a downgrade of what ships.

**Spec gap found here.** As written, CFC-2 fails only when a tool's go directive is *newer* than go.mod's. Both failures here go the other way: the tool's go directive is old enough, but its x/tools is too old to read the repo's Go. A check that runs each pinned analysis tool once against the repo under go.mod's Go would catch this; a go-directive comparison does not. This is proposed for CFC-2 / task 2.1, not changed here.

**What unblocks.** Choose A, B or C. Under A: rerun `task lint` once and `task vulncheck` five times on the bumped tree, record them here and tick 1.3.
