## T0.1 — probe

All verified 2026-10-19 on this host (Linux, `go1.27.2 linux/amd64`, Docker 29.9.0), with pgx
v5.11.0 and mongo-driver v1.17.10 from `go.mod`. The probe ran from a throwaway module outside
the repository (`/tmp/sct-probe`, `go.mod` requiring the same two versions, `go.sum` copied);
the code is summarised below, not committed. No assumption in `proposal.md` or `design.md` is
contradicted, so the loop continues.

### pgx: parsed TLS shape per sslmode

`pgxpool.ParseConfig("host=a,b user=u dbname=d sslmode=<m>")`, `HOME` set to an empty temp dir,
`PGSSLMODE` unset. `ISV` = `InsecureSkipVerify`, `VPC` = `VerifyPeerCertificate != nil`, `fb` =
`Fallbacks` in order. Output, verbatim apart from column alignment:

```text
sslmode=             main={ISV=true VPC=false SN="a"} fb[a]=nil fb[b]={ISV=true VPC=false SN="b"} fb[b]=nil
sslmode=disable      main=nil fb[b]=nil
sslmode=allow        main=nil fb[a]={ISV=true VPC=false SN="a"} fb[b]=nil fb[b]={ISV=true VPC=false SN="b"}
sslmode=prefer       main={ISV=true VPC=false SN="a"} fb[a]=nil fb[b]={ISV=true VPC=false SN="b"} fb[b]=nil
sslmode=require      main={ISV=true VPC=false SN="a"} fb[b]={ISV=true VPC=false SN="b"}
sslmode=require +rootcert   main={ISV=true VPC=true SN="a" RootCAs=true} fb[b]={... VPC=true ...}
sslmode=verify-ca    main={ISV=true VPC=true SN="a"} fb[b]={ISV=true VPC=true SN="b"}
sslmode=verify-full  main={ISV=false VPC=false SN="a"} fb[b]={ISV=false VPC=false SN="b"}
direct, unset        main={ISV=true VPC=false SN="a"}            (sslnegotiation=direct → require)
url unset            main={ISV=true VPC=false SN="a"} fb[a]=nil  (postgres://u@a/d)
```

- Unset sslmode behaves as `prefer`: TLS without verification, then a plaintext fallback
  (`fb[a]=nil`). `allow` starts plaintext. `sslrootcert` with unset/`prefer` still sets
  `ISV=true` and no callback: the CA is never checked. Verified.
- Each host gets its own `*tls.Config`; no fallback shares the main config's pointer (`same=false`
  for every fallback). So the CA must be set on the main config and on every fallback. Verified.
- `verify-ca` callback: with `RootCAs` set on the parsed (original) config, the callback of a
  `Config.Copy()` accepts a leaf signed by X (`err: <nil>`); with `RootCAs` set only on the copy,
  the copy's callback still rejects it. The closure reads `tlsConfig.RootCAs` of the pointer
  captured in `configTLS` (`pgconn/config.go:957-990`), and `Copy()` clones it
  (`pgconn/config.go:173`, `:185`). G3 must set `RootCAs` on the parsed config before
  `pgxpool.NewWithConfig`, not on a copy, or install its own callback. Verified.
- `PGSSLMODE=verify-ca` with no sslmode in the DSN yields the `verify-ca` shape; `PGSSLROOTCERT`
  with a valid file yields `RootCAs=true`. Both reach the parse. Verified.
- `PGSSLROOTCERT` missing: `ParseConfig` fails with
  ``cannot parse `host=sentinel-host user=sentinel-user password=xxxxx`: failed to configure TLS
  (unable to read CA file: open …/missing.pem: no such file or directory)``. The error text
  carries the DSN host and user (password masked). Malformed: `… failed to configure TLS (unable
  to add CA to cert pool)`. Design step 1 (check the sources before parsing, never echo the DSN)
  is therefore needed for D4. Verified.
- `HOME/.postgresql/root.crt` present: `RootCAs=true` with no DSN key (`pgconn/defaults.go:58`).
  `PGSERVICEFILE` entry with `sslrootcert`: selected by `service=s1` in the DSN and by
  `PGSERVICE=s1`, both give `RootCAs=true`; an entry pointing at a malformed file fails the parse
  with `unable to add CA to cert pool`. Verified.

### mongo-driver: connection-string keys

`connstring.Parse(uri)` output (`SSL`, `SSLCaFile`, `SSLInsecure`):

```text
?tls=true&tlsCAFile=/a&tlsCAFile=/b   SSL=true CaFile="/b" Options[tlscafile]=[/a /b]
?TLSCAFILE=/a                         SSL=true CaFile="/a"
?sslCertificateAuthorityFile=/a       SSL=true CaFile="/a"
?tlsCAFile=/a&tls=false               SSL=false CaFile="/a"
?TLSINSECURE=true&tls=true            SSL=true Insecure=true
?tlsInsecure=maybe                    ERR invalid value for "tlsInsecure": "maybe"
?tlsCertificateKeyFile=/k             SSL=true
?ssl=true                             SSL=true
```

- Keys match case-insensitively (`strings.ToLower`, `connstring.go:348`); a repeated key: the
  last value wins and `Options` keeps every value. `tls`/`ssl` given twice with different values
  is a parse error (`connstring.go:579-595`). Verified.
- Options that turn TLS on (`u.SSL = true`): `tls`/`ssl=true`, `tlsCertificateKeyFile` /
  `sslClientCertificateKeyFile`, `tlsCertificateFile`, `tlsPrivateKeyFile`, `tlsCAFile` /
  `sslCertificateAuthorityFile`, `tlsDisableOCSPEndpointCheck` (`connstring.go:597-645`). A later
  `tls=false` turns it off again even with `tlsCAFile` set. Verified (read and run).
- No DNS-free parse: `connstring.Parse` and `ParseAndValidate` always use `dns.DefaultResolver`
  (`connstring.go:99-100`); `connstring.Parse("mongodb+srv://sentinel-host.invalid/?tls=false")`
  returned `lookup _mongodb._tcp.sentinel-host.invalid … no such host` after 6 ms, and
  `ApplyURI` the same. The parser type with a pluggable resolver is unexported. So SCT-3's key
  check reads the query string itself (the design's stated fallback). For M3/M8 the test can
  assert no lookup by checking that the error is the kollect rejection, not a `lookup` error, on
  a `.invalid` host. Verified.
- Backstop: `ApplyURI("mongodb://h/?tlsCAFile=<valid file>")` gives `TLSConfig.RootCAs != nil`;
  `ApplyURI("mongodb://h/?tls=true")` gives a `TLSConfig` with `RootCAs == nil`. Verified.

### Go: replacing the system pool in a child process

A parent wrote root P and a P-signed leaf, then ran the probe binary as a child with
`SSL_CERT_FILE=P`:

```text
SSL_CERT_DIR=<empty dir>  child: SystemCertPool err=<nil> roots=1   verify P-signed leaf err=<nil>
SSL_CERT_DIR=""           child: SystemCertPool err=<nil> roots=123 verify P-signed leaf err=<nil>
parent (real system pool) verify P-signed leaf err != nil: true
```

An empty directory replaces the system pool with P alone; an empty value keeps Go's default
directories (123 roots). The test rule in `tasks.md` holds. Verified.

### Containers

Certificates from `openssl` (ECDSA P-256, CA X, server SAN `localhost`, `127.0.0.1`) in a temp
dir, copied into the container with `docker cp` (files arrive owned by the host uid).

- `postgres:16-alpine`: a key mounted or copied as-is fails (`could not load server certificate
  file … Permission denied`; the server runs as uid 70). What worked: entrypoint
  `sh -c 'install -o postgres -m 0600 /certs/server.key /var/lib/postgresql/server.key &&
  install -o postgres -m 0644 /certs/server.crt /var/lib/postgresql/server.crt &&
  exec docker-entrypoint.sh postgres -c ssl=on -c ssl_cert_file=… -c ssl_key_file=…'`. Then
  `psql "host=localhost port=55432 user=postgres sslmode=verify-full sslrootcert=/ca.pem"` returned
  `ssl = t`. Verified.
- `mongo:7` (the image `internal/sink/mongodb/export_integration_test.go:810` uses):
  `--tlsMode requireTLS --tlsCertificateKeyFile <cert+key PEM>` alone fails ("TLS without
  specifying a chain of trust is no longer supported"); a 0600 key file fails (`Permission denied`,
  the server runs as uid 999). What worked: the combined PEM at mode 0644 plus
  `--tlsCAFile /certs/ca.pem --tlsAllowConnectionsWithoutCertificates --bind_ip_all`. A TLS ping
  with `--tlsCAFile` returned `1`; a plaintext client was refused (`SSLHandshakeFailed`, "only
  allow SSL connections"). Verified.
